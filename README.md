# BUH-214 — расширение БП_КонтрольДолгов

Кредитный лимит покупателя, контроль при проведении «Реализации (акты, накладные, УПД)»
и отчёт «Просроченная дебиторская задолженность». Основная конфигурация БП 3.0 не меняется.

## Комментарий к сдаче

### Созданные объекты (префикс `кд_`)

| Объект | Назначение |
|---|---|
| `ОбщийМодуль.кд_КонтрольКредитногоЛимита` (сервер) | Расчёт долга и проверка лимита. Один запрос к регистру бухгалтерии на документ. |
| `Роль.кд_ОтгрузкаСверхЛимита` | Без прав на данные: её наличие позволяет провести реализацию сверх лимита (выводится только предупреждение). |
| `Отчет.кд_ПросроченнаяДебиторскаяЗадолженность` | СКД: остатки 62.01 по контрагенту / договору / документу расчётов, интервалы просрочки, лимит, превышение, условное оформление. |
| Реквизиты `кд_ЛимитЗадолженности` (Число 15.2, неотриц.), `кд_РазрешитьОтгрузкуСверхЛимита` (Булево) | Добавлены в заимствованный справочник «Контрагенты». |

### Заимствованные объекты

| Объект | Зачем |
|---|---|
| `Справочник.Контрагенты` | Новые реквизиты. |
| `Справочник.Контрагенты.ФормаЭлемента` | Группа «Кредитный лимит» (создаётся программно). |
| `Документ.РеализацияТоваровУслуг` | Перехват проведения. |
| `Справочник.Организации` | Тип параметра «Организация» в схеме отчёта. |
| `Подсистема.Продажи` | Отчёт в разделе «Продажи → Отчёты». |
| Роли `ДобавлениеИзменениеДанныхБухгалтерии` (профиль «Бухгалтер»), `ПолныеПрава`, `АдминистраторСистемы` (администратор) | Права «Использование» и «Просмотр» на отчёт. |
| Язык `Русский` | Обязателен для расширения. |

### Перехваченные события и почему именно они

**`Документ.РеализацияТоваровУслуг` → `&После("ОбработкаПроведения")`**

- **Почему `ОбработкаПроведения`.** Она выполняется на сервере, внутри транзакции проведения и при любом способе проведения: из формы, из списка, обработками. `Отказ = Истина` откатывает проведение целиком.
- **Почему не форма.** Клиентское `ПередЗаписью` в форме обходится проведением из списка и групповыми обработками.
- **Почему не `ПередЗаписью` объекта.** Оно срабатывает и при записи без проведения.
- **Почему `&После`, а не `&Вместо`.** Типовое проведение не трогаем. Проверку делаем, только если типовое проведение прошло (`Отказ` не установлен).
- **Что пропускается.** Групповое перепроведение (закрытие месяца) не является новой отгрузкой. Контроль в нём не выполняется, чтобы не блокировать регламентные операции.

**`Контрагенты.ФормаЭлемента` → `&После("ПриСозданииНаСервере")`**

Элементы добавляются кодом, XML формы не правится. Так расширение не зависит от раскладки типовой формы.

### Как считается долг

Долг = сальдо 62.01 (`СуммаОстаток`) по контрагенту и организации + `СуммаДокумента`.

- **Граница остатков** — `Новый Граница(МоментВремени(), ВидГраницы.Исключая)`. Движения самого документа отсекаются. Поэтому повторное проведение не учитывает сумму документа дважды. Результат не зависит и от того, включено ли в базе отложенное проведение расчётов.
- **Лимит 0 или флаг «Разрешить сверх лимита».** Проверка завершается до запроса к регистру: контрагент работает как раньше.
- **Текст сообщения:** «Превышен кредитный лимит контрагента …: лимит 100 000,00, долг с учетом документа 135 400,00». Для пользователя с ролью `кд_ОтгрузкаСверхЛимита` то же сообщение выводится как предупреждение, документ проводится.

### Отчёт

| Что | Как |
|---|---|
| Параметры | Дата отчёта (по умолчанию — сегодня), Организация (пусто — все), Срок оплаты по умолчанию (10 дней), отбор по контрагенту. |
| Срок оплаты | `ДоговорыКонтрагентов.СрокОплаты`, если в договоре установлен флаг `УстановленСрокОплаты`. Иначе — параметр отчёта. |
| Дата документа расчётов | Берётся из регистра `ДанныеПервичныхДокументов`, как в типовых отчётах БП. |
| Интервалы | Границы 30/60/90 — параметры схемы, в запросе нет чисел. |
| Остатки | На конец дня отчёта включительно, как в ОСВ. Кредитовые остатки по документам попадают в «Не просрочено», поэтому «Итого» по контрагенту совпадает с ОСВ по 62.01. |
| Лимит, превышение | Показываются в строках контрагента и его документов; в общем итоге не суммируются. |
| Условное оформление | Строки с превышением лимита выделяются фоном. |
| Обращения к регистру | Один пакетный запрос на весь отчёт. |

## Проверка и сдача — по шагам

Перед каждым .bat закрыть Конфигуратор и 1С:Предприятие (учебная версия: один сеанс).

1. **`load.bat`** → `Y`. Ждать `[OK] ... модули без ошибок`. При ошибке смотреть `load.log`.
2. **Форма контрагента** (один раз, в Конфигураторе):
   1. Конфигурация → Расширения конфигурации → `БП_КонтрольДолгов` → открыть.
   2. В дереве **основной** конфигурации: Справочники → Контрагенты → Формы → ФормаЭлемента → ПКМ → «Добавить в расширение» → `БП_КонтрольДолгов`.
   3. Открыть модуль заимствованной формы в расширении и вставить код из `tools\form\Контрагенты.ФормаЭлемента.Module.bsl`.
   4. F7 (обновить конфигурацию БД), закрыть Конфигуратор.
   5. `dump.bat`, чтобы форма попала в `src`.
3. **`testdata.bat`** — соберёт `build\кд_ТестовыеДанные.epf` и откроет 1С с ней. Если 1С спросит про открытие внешней обработки — разрешить. Обработка создаёт:

   | Покупатель | Лимит | Срок оплаты | Реализации (дней назад → интервал) | Оплата | Долг |
   |---|---|---|---|---|---|
   | «Ромашка (тест КД)» | 100 000 | по умолчанию, 10 дн. | 5 → не просрочено; 30 → 1–30; 55 → 31–60 | 15 000 по третьей | 120 000 — **превышение 20 000** |
   | «Лютик (тест КД)» | 0 | 20 дн. в договоре | 100 → 61–90; 150 → более 90 | — | — |
   | «Васильков (тест КД)» | 300 000 | по умолчанию | 40 → 1–30 | 20 000 | в пределах лимита |

   Ещё создаётся **непроведённая** реализация «Ромашки» на 15 400. Журнал — в окне сообщений и в `%TEMP%\kd_testdata.log`. Повторный запуск ничего не дублирует.
4. **Проверки и скриншоты:**
   1. **Скриншот 1.** Продажи → Реализация → открыть черновик «Ромашки» на 15 400 → «Провести». Ожидается отказ: «…лимит 100 000,00, долг с учетом документа 135 400,00».
   2. У «Лютика» (лимит 0) любая новая реализация проводится как раньше.
   3. Поставить «Ромашке» лимит ровно 120 000 и перепровести её реализацию за 5 дней назад на 50 000. Долг до документа — 70 000, с документом — 120 000, то есть проведение пройдёт. Если бы сумма документа учитывалась дважды, получилось бы 170 000 и отказ. После проверки вернуть лимит 100 000.
   4. **Скриншот 2 — роль.** Администрирование → Настройки пользователей и прав → Профили групп доступа → создать профиль с ролью «Отгрузка сверх кредитного лимита» и включить пользователя в группу доступа с этим профилем. Повторить проведение черновика: предупреждение, документ проведён.
   5. **Скриншот 3.** Продажи → Отчёты → «Просроченная дебиторская задолженность» → Сформировать. Все пять колонок заполнены, строки «Ромашки» выделены. Сверить «Итого» по контрагентам с ОСВ по счёту 62.01 на ту же дату (Отчёты → Оборотно-сальдовая ведомость по счёту → 62.01, детализация по контрагентам).
5. **`build-cfe.bat`** → `build\БП_КонтрольДолгов.cfe`.
6. Коммит: `git add -A && git commit` (или `_git-commit-auto.bat` с текстом в `_commit-message.txt`).

## Ограничения и допущения

- Контроль только в «Реализации (акты, накладные, УПД)». Не контролируются «Счёт покупателю», авансы 62.02 и счета 76 (вне рамок ТЗ).
- Сумма документа берётся как `СуммаДокумента` целиком, без учёта зачёта аванса.
- Роль проверяется через `РольДоступна`. Пользователь с «Полными правами» без этой роли тоже получает отказ: право сверх лимита выдаётся явно.
- Если в базе выключен учёт по документам расчётов (у 62.01 нет третьего субконто), отчёт не сможет определить дату долга. Весь долг попадёт в «Не просрочено», итоги при этом совпадут с ОСВ.
